# Batch 11 — Service-specific enquiries and submission recovery

Implemented on `main` after `2f27972`. This batch changes the shared enquiry form, the contact-page layout, and the API's verification-failure response. No dependencies were added.

## Visitor experience

- AWS, CI/CD, Kubernetes and DevOps enquiry links select the service and show a relevant heading, introduction and visible message guidance. Changing the priority updates that copy without clearing entered details. Ordinary contact visits and unsupported focus values use the general consultation copy.
- The contact page has one main heading and one introduction. On mobile, the form follows the introduction and the next-step explanation follows the form. Other pages keep their existing main headings and use the enquiry section as a subsection.
- Company and priority are explicitly optional. The page explains that an engineer replies within one business day, followed by a free 30-minute call and a discussion of the next step.
- Copy updates after hydration so a direct visit with a service query remains compatible with the shared prerendered contact HTML. The canonical URL remains `/contact`; query variants are not additional indexed pages.

## Failed submissions

- Entered details remain in the current form after a failed attempt. Verification is renewed after each attempt because a token can be consumed even if message delivery later fails.
- The API returns `verification_failed` alongside a plain-language message for a rejected security check. Existing validation, origin checks, rate limits, hostname/action checks and mail-delivery requirements remain in place.
- The form displays controlled messages for verification, validation, rate limiting and unsuccessful/unconfirmed delivery. Raw server responses, network exception text and invalid JSON are not shown to visitors. Every error includes a clickable email alternative.
- Submission is guarded while a request is pending and while required verification is unavailable. Requests are not automatically resubmitted.
- Errors receive keyboard focus and use an alert; the successful confirmation heading receives focus. Message guidance is associated with the textarea without becoming part of its label.
- Only a successful HTTP response with `success: true` clears the form and records the existing confirmed-lead event. Failures record the existing error event. Analytics parameter definitions are unchanged.

## Validation

- All 13 tests passed, including new API tests for expired/used verification and failed delivery followed by a fresh verified successful attempt. External verification and email delivery are mocked in these tests.
- Production build, application/API TypeScript, targeted ESLint, whitespace checks and all 14 prerendered-page SEO/hosting checks passed.
- A local browser harness using the real Contact and TurnstileWidget components simulated delivery failure, verification rejection, connection failure, an invalid response and rate limiting. Each check asserted that every entered field remained, a fresh verification token was issued, feedback received focus, an email alternative was present, and no confirmed-lead event was emitted.
- After those five failures, a successful retry produced exactly one confirmed-lead event and focused the confirmation heading. The harness also verified that an expired token disabled submission until renewed. No real enquiry or analytics event was sent.
- Direct visits for AWS audit, AWS cost reduction, CI/CD, Kubernetes, DevOps and an unknown focus loaded with the expected heading and service selection. Changing the service preserved the message. The built preview reported no browser errors.
- Desktop and a 390-pixel-wide mobile frame were inspected. The mobile document's client width and scroll width both measured 375 pixels (the frame reserves scrollbar space); no horizontal overflow was present. The first name field began around 636 pixels from the top.

Local screenshots and the isolated check fixture are retained under `docs/analytics/2026-10-13/verification/batch11/`. The fixture is not part of the production build. No production enquiry was submitted and no real CAPTCHA challenge was solved.

## Publication and limits

Source and checks are ready on `main`. Publication requires a new, commit-specific exception if GitHub still enforces administrator protection and a pull request. Earlier approvals applied only to their named commits.

Entered details are not stored across a full refresh or intentional page departure. If the server accepts a message but the browser loses the response, delivery remains uncertain; the page says it could not confirm receipt and leaves retrying to the visitor. An intentional retry in that situation can produce a duplicate email.
